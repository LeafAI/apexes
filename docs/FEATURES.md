# Apexes — Feature Tracking

> This is the **single source of truth** for feature-level status across the Apexes project. It is derived from the functional breakdown in [`docs/superpowers/specs/2026-07-28-apexes-vision-and-roadmap.md`](superpowers/specs/2026-07-28-apexes-vision-and-roadmap.md) (§2.2) and mapped to the sub-project roadmap (§3) in that same document.
>
> **Maintenance rule:** every feature row must map to exactly one roadmap sub-project (`#0`–`#15`). When a sub-project's design/plan/implementation cycle starts or finishes, update the status of every feature row it owns. Do not track feature status anywhere else (no parallel TODO lists) — this file is authoritative.

## Status legend

| Symbol | Meaning |
|---|---|

Wiring this in surfaced a genuine structural property: MarketEventBus holds its broadcast sender open for its whole connected lifetime, so a consumer's adapted stream does not end merely because the real upstream provider's own connection dropped (only a bus-level disconnect ends it) -- apexes-paper's run_paper_trading needed a take_until(stop_signal) production-code fix for this (apexes-backtest::run_event_loop only polls its stop signal once per loop iteration, unlike the other two consumers' tokio::select!-based loops which are unaffected), and all three consumers' doc comments now describe this accurately rather than the pre-integration behavior. Two caveats remain, both honestly documented rather than silently accepted: (1) this is in-process broadcast only -- genuine inter-process/multi-machine message-bus support (NATS JetStream or similar, row 8.3) remains unimplemented and separately deferred; (2) no current production entrypoint in this workspace actually runs two of these three consumers concurrently against the same bus in a real running system (only proven in tests) -- this is forward-looking infrastructure for a future multi-consumer deployment, not a fix for an observed production problem today. |
